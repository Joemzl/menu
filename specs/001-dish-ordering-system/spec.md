# Feature Specification: 点菜小程序 — 菜品浏览、下单、接单与H币货币系统

**Feature Branch**: `001-dish-ordering-system`

**Created**: 2026-06-15

**Status**: Draft

**Input**: User description: "菜品描述需要有示意图标和菜品名称，菜品是可以增加和减少的。需要左侧菜品分类栏，按照早餐、晚餐、零食和饮品分类。点菜端：点菜操作应该有个加号和减号按钮，需要有购物车可以查看自己的点菜记录，有下单按钮可以提交点菜记录，以及历史订单可以看到点单记录，历史订单可以看到刚刚下单状态：已下单、已接单、已完成。厨师端：收到订单的消息列表，消息列表打开有接单按钮，接单后出现完成按钮。主要需求：货币系统。点菜需要货币：H币。点菜端每个月有10000个H币，每道菜有不同的价格，点菜端点菜需向厨师端支付H币。每当完成一道订单后，点菜端可以给这个订单打分，1-5分，按照分数来奖励额外的H币。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 菜品管理与分类浏览 (Priority: P1)

菜品提供方（厨师/管理员）录入菜品信息，包括菜品示意图标、名称、价格和所属分类。点菜用户可以按分类（早餐、晚餐、零食、饮品）浏览菜单，左侧分类栏可切换，右侧展示对应菜品列表。

**Why this priority**: 菜品是系统的核心数据，没有菜品就无法进行任何点菜操作。这是整个系统的数据基础。

**Independent Test**: 创建一份菜单，添加至少4道分属不同分类的菜品（每道含图标+名称+价格），通过微信分享链接发给另一用户，该用户可看到分类栏和菜品列表并能切换分类。

**Acceptance Scenarios**:

1. **Given** 菜单为空，**When** 管理员添加一道菜品（含图标、名称"豆浆"、分类"早餐"、价格50H币），**Then** 早餐分类下出现该菜品卡片，展示图标和名称。
2. **Given** 菜单已有多个分类的菜品，**When** 用户点击左侧"零食"分类，**Then** 右侧展示区域切换为零食分类下的所有菜品。
3. **Given** 菜单已有某菜品，**When** 管理员删除该菜品，**Then** 该菜品从所有用户的分类列表中消失。
4. **Given** 已有菜品，**When** 管理员修改菜品价格，**Then** 所有用户看到的该菜品价格立即更新。

---

### User Story 2 - 点菜、购物车与H币支付 (Priority: P1)

点菜用户在菜品列表中使用加减号按钮调整点菜数量，购物车实时汇总已选菜品及总价。用户确认后点击下单按钮，系统扣除对应H币并向厨师端发送订单。

**Why this priority**: 这是点菜端的核心交互，直接影响用户的点菜体验和H币系统的运转。

**Independent Test**: 用户浏览菜单后点击加号选择2份馒头（30H币/份）、1杯橙汁（20H币/份），购物车显示总价80H币，点击下单后H币余额减少80，厨师端收到新订单。

**Acceptance Scenarios**:

1. **Given** 用户H币余额为10000，菜品"豆浆"价格为50H币，**When** 用户点击该菜品的加号按钮，**Then** 数量变为1，购物车总价显示50H币。
2. **Given** 用户已将"豆浆"数量设为2，**When** 用户点击减号按钮，**Then** 数量减少为1，购物车总价对应减少。
3. **Given** 用户购物车中有总价200H币的菜品，H币余额为10000，**When** 用户点击"下单"按钮，**Then** 订单提交成功，H币余额变为9800，购物车清空。
4. **Given** 用户购物车总价为12000H币，H币余额仅为5000，**When** 用户点击"下单"按钮，**Then** 系统提示"H币不足，请调整菜品数量"，订单不提交。
5. **Given** 用户购物车为空，**When** 用户点击"下单"按钮，**Then** 系统提示"请先选择菜品"。

---

### User Story 3 - 厨师端订单处理 (Priority: P1)

厨师端收到新订单推送/刷新后可见订单消息列表。点开订单详情后可看到菜品明细，点击"接单"按钮接单，接单后显示"完成"按钮，制作完毕点击"完成"按钮标记订单完成。

**Why this priority**: 没有厨师端处理，点菜就失去了闭环。这是订单流转的关键环节。

**Independent Test**: 点菜端提交一份订单后，厨师端消息列表中出现该订单，厨师点击接单→订单状态变为"已接单"，厨师点击完成→订单状态变为"已完成"。

**Acceptance Scenarios**:

1. **Given** 点菜端提交了一份新订单，**When** 厨师打开订单消息列表，**Then** 列表中展示该订单的摘要（下单人、总价、时间）。
2. **Given** 厨师打开一条状态为"已下单"的订单详情，**When** 厨师点击"接单"按钮，**Then** 订单状态变为"已接单"，按钮变为"完成"。
3. **Given** 厨师打开一条状态为"已接单"的订单详情，**When** 厨师点击"完成"按钮，**Then** 订单状态变为"已完成"，按钮消失。
4. **Given** 厨师已接单，**When** 点菜端查看该订单，**Then** 状态显示"已接单"。

---

### User Story 4 - 订单历史与状态追踪 (Priority: P2)

点菜端和厨师端均可查看历史订单记录。点菜端历史订单展示订单状态（已下单、已接单、已完成），每个订单显示菜品明细和下单时间。厨师端历史订单可按状态筛选。

**Why this priority**: 订单历史是用户体验闭环的重要部分，但不影响核心下单接单流程，可在MVP后快速迭代。

**Independent Test**: 点菜端提交3份订单（分别处于已下单、已接单、已完成状态），进入历史订单页面，看到3条记录各有不同状态标签。

**Acceptance Scenarios**:

1. **Given** 点菜端提交了一份订单，**When** 进入"历史订单"页面，**Then** 看到该订单显示"已下单"状态标签。
2. **Given** 厨师接单后，**When** 点菜端刷新历史订单，**Then** 该订单状态从"已下单"更新为"已接单"。
3. **Given** 厨师完成订单后，**When** 点菜端刷新历史订单，**Then** 该订单状态更新为"已完成"。
4. **Given** 厨师端有多条不同状态的订单，**When** 厨师按"已完成"状态筛选，**Then** 仅显示已完成订单。

---

### User Story 5 - 订单评分与H币奖励 (Priority: P2)

订单完成后，点菜端可对该订单进行1-5星评分。系统根据评分自动计算并发放额外H币奖励（如5星200H币、4星100H币、3星50H币、1-2星不奖励）。奖励即时到账。

**Why this priority**: 评分与奖励是激励机制，属于锦上添花功能，不影响核心交易流程。

**Independent Test**: 一份订单完成后，点菜端进入历史订单对该订单评分4星，H币余额立即增加对应奖励金额。

**Acceptance Scenarios**:

1. **Given** 一份订单状态为"已完成"且尚未评分，**When** 点菜端进入该订单详情，**Then** 显示1-5星的评分入口。
2. **Given** 点菜端对已完成订单评5星，**When** 提交评分，**Then** H币余额增加200，该订单标记为"已评分"，评分入口消失。
3. **Given** 点菜端对已完成订单评2星，**When** 提交评分，**Then** H币余额不变（不增不减），该订单标记为"已评分"。
4. **Given** 订单已完成超过7天尚未评分，**When** 点菜端尝试评分，**Then** 系统提示"评分已过期"。

---

### Edge Cases

- 用户H币余额刚好等于购物车总价时下单，余额归零，订单正常提交。
- 用户当月H币用完（余额为0），无法提交任何订单，直到下月重置。
- 同一用户多次提交同一菜品订单，系统分别生成独立订单号，不合并。
- 厨师端同时收到多条新订单时，消息列表按时间倒序排列，最新订单在最上方。
- 用户在下单过程中（购物车已有菜品但未提交），厨师修改了菜品价格——系统锁定已加入购物车的价格为加入时价格，避免下单时价格变化导致体验问题。
- 网络异常导致下单请求发送成功但客户端未收到确认——系统需要幂等处理，防止重复扣款。
- 厨师删除某菜品后，已加入该菜品的购物车记录如何处理（是否自动清退该菜品）。
- H币每月1日0点自动重置为10,000，未用完的余额不累计到下月。
- 点菜端在"已下单"状态取消订单，H币全额退还并记录流水，订单状态变为"已取消"。
- 取消后退还的H币可能使用户余额超过10,000（如当月有评分奖励+取消退款）。
- 菜单过期后，已下单但未接单的订单仍可由厨师接单和完成（不因菜单过期影响已在途订单）。
- 过期菜单的点菜端页面显示"菜单已结束"提示，禁止±操作和下单，但仍可查看菜品列表。
- 密码保护菜单：错误的分享链接不携带密码，点菜端进入时弹出密码输入框，连续3次输入错误锁定30秒。
- 某分类下无菜品时，分类标签仍显示，右侧展示区域显示"该分类暂无菜品"文字提示。
- 全部四个分类均无菜品时，显示"暂无菜品，等待厨师添加"占位提示。
- 购物车为空时，购物车页面显示"购物车空空如也"占位提示（FR-010已有校验）。
- 厨师完成订单后，订单金额从点菜端扣除时转入厨师余额，H币流水记录两条：点菜端支出 + 厨师端收入。
- 点菜端取消订单时，仅退还H币给点菜端（厨师未接单，不涉及转账）。

## Requirements *(mandatory)*

### Functional Requirements

**菜品管理**:
- **FR-001**: 系统 MUST 支持菜品录入：示意图标、菜品名称、单价（H币）、所属分类。
- **FR-002**: 系统 MUST 支持四个固定分类：早餐、晚餐、零食、饮品。分类列表以左侧栏形式展示。
- **FR-003**: 系统 MUST 支持菜品的增加和删除操作，删除后所有用户端实时同步。
- **FR-004**: 系统 MUST 支持修改菜品信息（名称、图标、价格），修改后即时生效。
- **FR-005**: 菜单创建时 MUST 设置截止时间（默认当前时间+24小时），过期后禁止新订单提交，但允许查看历史订单。厨师可手动调整截止时间。
- **FR-006**: 菜单默认公开访问（有分享链接即可进入），厨师可选设置4位数字密码。设置密码后，点菜端进入菜单需先输入密码验证。

**点菜与购物车**:
- **FR-007**: 点菜端 MUST 每个菜品卡片提供加号（+）和减号（-）按钮，用于调整点菜数量（最低为0即不点）。
- **FR-008**: 系统 MUST 提供购物车视图，实时展示已选菜品列表、各菜品数量、单价小计和总价（H币）。
- **FR-009**: 系统 MUST 在下单时校验用户H币余额是否足够支付购物车总价，不足则拒绝下单并提示。
- **FR-010**: 系统 MUST 在下单时校验购物车非空，空购物车不允许下单。
- **FR-011**: 下单成功后，系统 MUST 立即从点菜端H币余额中扣除对应金额。

**H币货币系统**:
- **FR-012**: 每位点菜用户每月 MUST 自动获得10,000 H币额度。厨师初始余额为0，仅通过完成订单获得H币收入。
- **FR-013**: 系统 MUST 记录每笔订单的H币支付金额，不可篡改。
- **FR-014**: H币余额 MUST 在用户端（点菜端和厨师端）实时可见。
- **FR-015**: 订单完成后（状态变为"已完成"），下单时扣除的H币 MUST 自动转入厨师账户余额。
- **FR-016**: 厨师端 MUST 可查看自己的H币收支流水（订单收入 + 月度重置）。

**厨师端订单处理**:
- **FR-017**: 厨师端 MUST 展示订单消息列表，包含订单摘要信息（下单人、总价、时间、状态）。
- **FR-018**: 订单详情 MUST 提供"接单"按钮（状态为"已下单"时可见）。
- **FR-019**: 接单后，"接单"按钮 MUST 替换为"完成"按钮。
- **FR-020**: 点击"完成"后，订单状态 MUST 变更为"已完成"，按钮消失，同时下单时扣除的H币转入厨师余额。

**订单取消**:
- **FR-021**: 点菜端 MUST 可在订单状态为"已下单"时取消订单，取消后H币全额退还，订单状态变更为"已取消"。
- **FR-022**: 订单一旦进入"已接单"状态，MUST NOT 允许取消。

**订单状态与历史**:
- **FR-023**: 系统 MUST 支持四种订单状态：已下单、已接单、已完成、已取消。
- **FR-024**: 点菜端 MUST 提供"历史订单"入口，展示用户本人的所有历史订单及其状态。
- **FR-025**: 厨师端历史订单 MUST 支持按状态筛选。

**评分与奖励**:
- **FR-026**: 订单完成后，点菜端 MUST 可对该订单进行1-5星评分。
- **FR-027**: 系统 MUST 根据评分自动计算奖励H币：5星=200H币，4星=100H币，3星=50H币，1-2星=0H币。
- **FR-028**: 已评分的订单 MUST NOT 允许重复评分。
- **FR-029**: 超过7天未评分的已完成订单，系统 MUST 关闭评分入口。

### Key Entities

- **菜品（Dish）**: 图标URL、名称、价格（H币）、分类（早餐/晚餐/零食/饮品）、是否可用。属于某个菜单。
- **菜单（Menu）**: 菜品列表、创建者、创建时间、截止时间、访问密码（可选4位数字，null表示公开）、分享链接。一个菜单可被多人访问点菜。过期后禁止新订单。
- **订单（Order）**: 下单人、菜品明细（菜品+数量+单价小计）、总价（H币）、状态（已下单/已接单/已完成/已取消）、创建时间、接单时间、完成时间、取消时间、评分（1-5，可为空）、奖励H币。
- **用户（User）**: 微信OpenID、昵称、头像、角色（点菜端/厨师端）、H币余额、H币获得/消耗记录。所有用户（含厨师）均有独立H币账户。
- **H币流水（CoinTransaction）**: 用户、金额（正为收入负为支出）、类型（月度发放/下单扣款/订单收入/评分奖励）、关联订单、时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 点菜用户从浏览菜单到提交订单可在60秒内完成（3次以上菜品的选择+下单）。
- **SC-002**: 厨师端收到新订单的通知延迟不超过3秒。
- **SC-003**: 点菜端下单后H币余额变更在1秒内反映到用户界面。
- **SC-004**: 订单状态变更（接单/完成）在3秒内同步到点菜端历史订单页面。
- **SC-005**: 90%的用户能够在首次使用时独立完成点菜流程，无需额外指引。
- **SC-006**: H币扣款逻辑100%准确（无多扣、漏扣、重复扣款）。
- **SC-007**: 系统支持同一菜单下至少20人同时点菜，无数据错乱或性能降级。
- **SC-008**: 评分奖励H币在评分提交后即时到账（1秒内）。
- **SC-009**: 订单完成后，点菜端扣款+厨师端入账在1次事务中原子完成，金额一致无偏差。

## Clarifications

### Session 2026-06-15

- Q: 订单取消与H币退还策略？ → A: 点菜端可在"已下单"状态取消订单，H币自动全额退还。已接单或已完成不可取消。
- Q: 菜单生命周期 — 是否有截止时间？ → A: 菜单创建时设置截止时间（默认24小时），过期后禁止新订单但可查看历史。
- Q: 菜单访问控制 — 是否需要密码保护？ → A: 默认公开（有链接可访问），厨师可选设置4位数字密码。
- Q: 空分类与空购物车状态 — 如何展示？ → A: 分类为空时仍显示标签，右侧显示"该分类暂无菜品"文字提示。
- Q: 厨师端H币收款 — 厨师是否需要H币余额和账户？ → A: 厨师有独立H币余额，初始余额为0，仅通过完成订单获得收入，不享受月度10,000 H币发放。

## Assumptions

- 用户通过微信授权登录，每个用户有唯一身份标识（OpenID），无需额外注册流程。
- "用户A"为菜单创建者/厨师，"用户B"为点菜端用户。同一个微信账号可同时拥有两种角色（作为厨师创建自己的菜单，也作为食客去别人的菜单点菜），两种角色共享同一H币账户。用户首次登录时：点菜端余额=10,000，厨师端余额=0。
- H币每月1日0点重置为10,000（用户设定的金额为10000而非10000w，已按10,000处理）。
- 购物车数据仅本地暂存，不同菜单之间的购物车独立（切换菜单需清空）。
- 菜品无库存概念，只要菜单中有该菜品即可无限下单。
- 菜品价格以加入购物车时的价格为准（锁定价格），避免下单时价格已变导致体验问题。
- 菜单分享通过微信小程序自带分享能力实现，分享卡片打开即进入点菜页面。密码保护菜单的分享卡片不携带密码，需接收者手动输入。
- 本系统为单人厨师场景（一个菜单对应一个厨师），暂不支持多厨师协作。
- 菜单默认有效期为创建后24小时，厨师可手动调整。过期后禁止新下单但允许查看历史。
